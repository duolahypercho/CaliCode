# Image generation

Status: **spec, not built.** Written 2026-08-15.

## 0. The decision in one paragraph

`image3d_mesh` already turns a reference image into a textured three.js mesh,
and its own description advertises a source it cannot produce: *"images
generated by an image model and imported via `asset_import_file`"*. Nothing in
core generates one. This adds the missing first step — one tool that calls an
image model, registers the result as a project asset, and hands back an
`assetId` the existing pipeline already accepts. The mesh half is not touched.

## 1. What exists, and where the seam is

The pipeline downstream of a generated image is complete:

| Step | Owner | Status |
| --- | --- | --- |
| produce an image | — | **missing** |
| register bytes as a project asset | `image3d::register_source_bytes` | done |
| image → mesh | `image3d_mesh` → `image3d::generate_mesh_asset` | done |
| mesh → scene / glTF | `image3d::export_gltf`, editor tools | done |

`register_source_bytes(root, slug, bytes) -> Result<String>` returns the asset
id. That return value is the seam: the new tool ends there, and every existing
tool takes it from that point. `asset_import_file` is the general-purpose
alternative (it takes `name`, `data`, `mime`, `tags`), and is the right target
when the image is meant for the asset library rather than for meshing.

There is already a precedent for core calling a model directly:
`image3d::review` builds OpenAI-style multimodal content and hands it to
`model::chat`, which forwards messages verbatim. Generation cannot reuse that
path — see §3 — but it can reuse the config and key resolution around it.

## 2. Which model, and why not a literal

The models.dev catalogue the client already ships knows which models emit
images (`modalities.output` contains `"image"`). Today's catalogue:

| Provider | Models |
| --- | --- |
| OpenAI | `gpt-image-2`, `gpt-image-1.5`, `gpt-image-1-mini` |
| Google | `gemini-3-pro-image`, `gemini-3.1-flash-image` |
| xAI | `grok-imagine-image`, `grok-imagine-image-quality` |
| OpenRouter | `openai/gpt-5-image`, `google/gemini-3-pro-image` |

Anthropic and DeepSeek have none, which matters: **the configured provider
today (`codex-router`) exposes only text models**, so the tool must degrade to
a legible error rather than a confusing one.

Selection mirrors `guardianModel` exactly, and for the same reason (AGENTS.md,
"Model catalog" — core holds no model list):

1. the client sends `imageModel` with the turn, chosen from models.dev by a
   new `reduceImageModels` in `modelMeta.ts`, sibling to `reduceGuardianModels`;
2. `assets.image_model` in `~/.cali/config.yaml` stands in when the client
   sends none;
3. absent both, the tool fails with a message naming both places to set it.

Note the third case is the default state on this machine. It must not read as
a bug in the tool.

## 3. The endpoint problem, stated honestly

`model::chat` speaks `/v1/chat/completions`. Image generation does not. Three
shapes are in play:

- **OpenAI-compatible `/v1/images/generations`** — OpenAI, xAI, and OpenRouter
  accept it. Response carries `data[0].b64_json` or a URL.
- **OpenAI Responses API** — what `gpt-image-*` increasingly prefers, and what
  `model.rs` already has a branch for (`chat_once_responses`).
- **Gemini native** — a different request body again, reached through
  `generateContent` with an image-capable model.

Do not paper over this with one adapter that "mostly works". Ship the
OpenAI-compatible shape first, because it covers OpenAI, xAI and OpenRouter —
which is every provider a user is likely to point at — and refuse an
unsupported one by name. A silent fallback that returns a text apology as if
it were an image is the failure worth designing against: the model would then
hand `image3d_mesh` a base64 blob of prose.

A URL response must be fetched and stored, not stored as a URL. An asset that
points at a provider CDN is an asset that expires.

## 4. Tool surface

```
asset_generate_image {
  slug:        string   // project
  name:        string   // asset name
  prompt:      string   // what to draw
  size?:       string   // "1024x1024" default; passed through, not validated
                        // against a hardcoded list — providers differ
  transparent?: boolean // background removal where supported; ignored elsewhere
}
  -> { assetId, name, mime, bytes, width, height, model }
```

`assetId` is the whole point of the return value: the next call is
`image3d_mesh { slug, assetId, mode }`, and the model should be able to read
that from the result without being told.

**Access: `Guarded`.** It spends real money per call. That is not a formality —
it is exactly the class of call the Auto guardian is built to stop, and the
live guardian test already shows it asking `"this will spend credits to
generate the 3D hero mesh"` for the neighbouring tool. Classifying this
`ReadOnly` would let an unattended `/loop` spend without a prompt.

`is_destructive` must agree. It answers from `core_tool_access` for core
tools, so declaring `Access::Guarded` in the literal is sufficient — but add
the assertion to `the_guarded_set_is_exactly_what_it_was` so the classification
cannot be quietly changed later.

## 5. Where the code goes

| File | Change |
| --- | --- |
| `core/src/imagegen.rs` | **new** — request shape, response decode, URL fetch, byte bounds |
| `core/src/tools.rs` | `ToolDef` literal + dispatch arm; `PLAN_DOCUMENT`-style const for the default size |
| `core/src/agent.rs` | `AgentOptions.image_model`, inherited by `SpawnParent` like `guardian_model` |
| `core/src/rpc.rs` | read `imageModel` from turn params |
| `core/src/config.rs` | `AssetsConfig { image_model: Option<String> }` |
| `client/src/lib/modelMeta.ts` | `reduceImageModels`, cached with the rest (bump `CACHE_KEY`) |
| `client/src/components/editor/AgentPanel.tsx` | send `imageModel` with the turn |

Two things to reuse rather than rebuild: `model::http_client()` (one shared
connection pool — building a client per request throws away keep-alive), and
the router-key branch in `chat_once`, which reads
`~/.codex/codex-router/internal-secret` when the provider is `codex-router`.
Both are easy to miss and both were learned the hard way.

## 6. Failure modes to design for, not discover

- **No image model configured.** The default state here. Name both places to
  set one; do not say "unsupported".
- **The configured provider has no image model.** `codex-router` today. Say
  which provider, and that its catalogue has none.
- **Content policy refusal.** Surface the provider's own words. A generic
  "generation failed" sends the model back to retry the same prompt.
- **A text model pointed at by mistake.** Refuse on response shape, loudly.
- **Enormous payloads.** A 4k PNG is megabytes; bound it the way
  `EDIT_MAX_WRITE_BYTES` bounds writes, and never let raw base64 into a tool
  result — return the `assetId` and let the asset live on disk.

## 7. Verification

- Unit: mock provider returning `b64_json` → asset registered, `assetId`
  returned, bytes on disk match.
- Unit: mock returning a URL → fetched and stored, not stored as a URL.
- Unit: text-shaped response → refused with the shape error, no asset written.
- Unit: no model configured → error names `assets.image_model` and the client.
- Unit: `Guarded`, and present in the guarded-set golden test.
- Round trip: generated `assetId` → `image3d_mesh` → mesh asset registered.
  This is the claim the whole spec exists to support; without it the pieces
  can each pass while the seam does not hold.
- Live, `#[ignore]`d, like `guardian::tests::live` and `browser::tests::live`:
  one real generation against whatever the operator has configured. CI cannot
  run it, and it is the only test that proves the request shape is right.

## 8. Open questions

1. **Does the router proxy image endpoints at all?** It is down as of writing,
   so this is unverified. If it does not, the practical path is a second
   provider preset (OpenAI or xAI) used only for images — which the design
   already allows, since `imageModel` carries `provider:model`.
2. **Library or mesh source?** `register_source_bytes` and
   `asset_import_file` write to different places. Suggest: register for
   meshing (the stated need), with a `library: true` flag later if wanted.
3. **Should the client show the image?** A generated asset the user cannot see
   until it becomes a mesh is hard to judge. Out of scope here; worth a row in
   the asset panel.
